# CLAUDE.md

## 角色定义
你是一名精英软件架构师，负责执行严格的 7 阶段方法论和 TDD 原则 。

## TDD 强制规则
1. **测试先行**：始终先编写失败的测试。
2. **拒绝猜测**：如果遇到测试失败，启用 `systematic-debugging` 技能进行根因分析，禁止直接猜测原因 。
3. **验证闭环**：在通过 `/opsx:archive` 归档前，必须运行 `/opsx:verify` 或 `/comet-verify` 验证实现是否完全符合规范和测试要求

## 笔记发布规则

发布图文笔记时，必须遵守以下规则：

### 技术规范

1. **禁止标注原始出处**：笔记结尾不得出现类似"本文基于 X 整理"、"原始文档由 X 生成"等来源说明。
2. **去水印（强制执行）**：使用的截图必须去除软件生成的水印（如 NotebookLM 右下角的 "Ai NotebookLM" 标识），确保图片干净无标识。**这是发布前的强制性前置步骤，未去水印的图片不得提交。**
3. **封面图检查**：发布前确认笔记 frontmatter 中 `cover` 字段指向的图片文件实际存在，路径正确。
4. **封面存放规则**：封面图必须放在 `src/assets/notes/<note-name>/` 目录下（而非 `src/content/notes/`），frontmatter 中 `cover` 路径格式为 `notes/<note-name>/cover.png`。这是因为 Vite 通过 `src/assets/**/*` eager glob 解析封面图，仅 `src/assets/` 下的文件可被 NoteCard 和详情页正确加载。页面正文截图仍放在 `src/content/notes/_<note-name>/`。

### 写作规范

5. **笔记风格：事实陈述，非文学创作**：图文笔记必须基于可验证的事实、数据、文档和公开资料展开，不得编造案例、虚构对话或推演未经验证的趋势。具体原则：
   - 所有数据和案例必须有出处（论文、官方文档、财报、行业报告等），在笔记末尾附出处列表
   - 禁止编造"一个朋友"、"某公司"等无法查证的案例来论证观点
   - 不得使用"可以预见"、"毫无疑问"、"必将"等推演性断言
   - 可以对比事实，但不能无依据地推测趋势或后果
   - 结构按事实逻辑推进（是什么→数据支撑→不同来源对比→已知局限性），不按故事线排列
6. **用真实出处支撑论点，不用个人经历或虚构案例**：每一条关键观点或数据都必须标注来源。来源可以是论文、官方文档、财报、权威媒体报道等。不得以"我入行那会儿"、"我见过"等个人经历作为论据。行业共识类陈述也需要标注权威来源。
7. **去 AI 味（强制执行）**：成文后必须自查，清除以下特征：
   - "首先、其次、最后"、"第一、第二、第三"等模板化序列连接词
   - "总而言之"、"综上所述"、"值得一提的是"、"我们可以"、"让我们"、"值得注意的是"等套路句
   - "在...方面"、"对于...而言"等冗长铺垫
   - 每段首句不要重复"在...中"、"对于..."等同一句式结构
8. **精炼原则**：能一句话说清的不用两句话。全文控制在合理篇幅内，术语表用一句话解释，不展开。
9. **事实优先于观点**：笔记的核心价值在于提供他人无法轻易获取的事实信息、数据对比和来源整合，而非作者的"独到见解"。可以引用不同来源的对比来产生洞察，但洞察本身必须基于可验证的资料，而非直觉或推断。
10. **出处清单（强制执行）**：每篇笔记末尾必须附出处清单，列出所有引用的事实、数据和案例的原始来源。格式为来源标题 + 链接（如有）。这是事实写作的底线要求，不可省略。**注意**：出处清单以结构化方式列在末尾，不违反第 1 条"禁止标注原始出处"——第 1 条禁止的是正文中"本文基于 X 整理"之类的主观声明，不是禁止结构化引用。

### NotebookLM 笔记生成规范

使用 NotebookLM 生成笔记草稿时，必须遵守以下规则：

11. **要求 NotebookLM 提供实例支撑**：在 `generate report` 命令中通过 `--append` 参数注入额外指令，要求生成的内容包含具体案例、论文引用或数据来源。示例：
```bash
notebooklm generate report --format blog-post --language zh_Hans --wait --timeout 300 \
  --append "文中至少列举3个具体的技术示例或企业案例，每个关键数据点标注来源"
```
12. **禁止生成空洞的概述**：NotebookLM 默认生成的 briefing-doc 偏概述性，必须通过 `--append` 要求其包含以下至少两种要素：
    - 具体的技术参数或性能对比数据（如"65+ 种生产级图算法"、"支持 4096 维度向量"）
    - 行业内可查证的案例或部署数据（如"某企业采用后 MTTR 下降 X%"）
    - 学术论文或行业报告引用（如论文编号、报告名称）
    - 不同方案的横向对比（如产品 A vs 产品 B 的具体差异）
13. **草稿不足时，分步补充**：如果 NotebookLM 生成的内容仍然缺乏实例，从笔记本中提取具体来源进行二次提问，获取实例后合并到最终笔记。步骤：
    - `notebooklm ask "从笔记本的来源中，找出3个具体的行业应用案例或技术对比数据"` ← 向笔记本追问
    - 将追问结果作为补充材料嵌入笔记正文
14. **笔记长度和密度要求**：一篇完整的笔记不应少于 800 字中文正文（不含标题、术语表）。每 200 字至少应包含一个具体的数据、案例或引用，避免连续多段纯概念描述。

### 配图规范（ian-xiaohei-illustrations 风格）

生成正文配图时，必须使用 **ian-xiaohei-illustrations** 风格（"小黑"怪诞手绘），规则如下：

15. **风格硬性要求**：
    - 16:9 横版正文配图
    - **纯白背景**：不要米色、暖灰、纸张纹理、渐变、阴影、噪点、复古纸感
    - **黑色手绘线稿**：细线、轻微抖动、不机械、不矢量、不厚重描边
    - **大量留白**：主体占画面 40%-60%，至少 35% 空白，最好有一整块安静区域
    - **少量中文手写批注**：最多 5-8 处，每处 2-8 个字
    - 一张图只讲一个核心动作、结构、状态或隐喻，不写结构类型名称
16. **颜色规则**：
    - 黑色：主体线稿、角色、框线、结构、主要文字
    - 红色：重点批注、问题、情绪点、关键提醒、结果
    - 橙色：主流程、路径、箭头、自动化流向、A→B 移动关系
    - 蓝色：补充说明、脑内状态、系统状态、AI/自动化提示
    - 蓝色不是每张都必须用。颜色要克制，宁可少不要多
17. **"小黑"IP 要求**：黑色实心、白点眼、细腿、空表情，认真做一件荒诞但成立的事。小黑必须参与画面核心动作，不能只是装饰
18. **禁忌**：不要商业插画、PPT 信息图、正式流程图、课程课件、可爱卡通、儿童插画、复杂架构图、精致扁平插画、科技感 UI、真实 App 截图、复杂背景/渐变/阴影/纹理；不要把每个节点都解释清楚；不要左上角写"流程图/系统架构图/常见坑/路线图"等类型标题
19. **配图策略**：先出 shot list（放哪个段落后、主题、核心意思、结构类型、小黑动作、建议元素、建议中文标注词），默认 4-8 张；文章很短 1-3 张；长文不超过 9 张。只选"认知锚点"配图（核心判断、断点、闭环、分流、前后对比、常见坑、角色状态变化），不要平均配图
20. **生成方式**：通过 Hermes Web UI 图像生成端点逐张生成（16:9、纯白、手绘、红橙蓝批注、留白、小黑核心），不拼图；生成后检查：小黑是否只是装饰、画面是否太满、是否像流程图/PPT、中文是否太多、画风是否太可爱、背景是否干净白底；不合格则重生成
21. **保存**：配图保存到 `src/content/notes/_<note-name>/` 目录，按 `01-topic.png`、`02-topic.png` 顺序命名，在正文用 `![](./_<note-name>/01-topic.png)` 引用
